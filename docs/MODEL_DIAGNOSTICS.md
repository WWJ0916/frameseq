# CogVideoX-2B：如何判断“接入成功”

当前已按固定验收配置开放实验预览，旧暂停与失败证据保留。下载完成、能编码MP4、产生可见主体和对多种输入稳定可用，是不同验收条件；本项目没有用前两项冒充最后一项。

## 已取得的证据

- 官方权重来自[官方模型的ModelScope镜像](https://modelscope.cn/models/ZhipuAI/CogVideoX-2b)，模型说明见[原始模型仓库](https://huggingface.co/zai-org/CogVideoX-2b)。本轮逐字节读取两个文本编码器分片、Transformer及VAE的全部权重，SHA256均匹配下载时保存的官方元数据，没有因白屏反复下载模型。
- 首次纸船配置为FP16 Transformer、CPU FP32文本编码器、FP16 VAE、原生Diffusers输出、DDIM、20步、种子42，720×480、49帧、8fps。2026年10月21日准确重跑得到相同MP4哈希：`37880b38a35d020087332176afed2512e3a7fa2988106c1fd7ff44f060bcd025`。接触表可见蓝色纸船与水波变化；只能证明这个固定样例可复现。
- 新纸船运行506.383秒，含温度等待；峰值已分配显存8,246,576,640字节。首次为249.449秒；不能将包含降温等待的差异称为算力回归结论。

## 对照与结论

| 实验 | 实际观察 | 可以得出的结论 |
| --- | --- | --- |
| 玩具车20步，FP16 VAE | 可解码但接近白屏 | 编码成功不代表生成内容成功 |
| 同类玩具车20/50步，FP32 VAE | 纯色检查失败 | 不能声称提高VAE精度已经修复 |
| 玩具车全FP32 | 仍为退化输出 | 单纯提高计算精度没有解决这个失败样例 |
| 玩具车种子42，FP16原生输出 | 近白细纹通过旧阈值，人工拒绝 | 质量启发式存在漏检，新增近白纹理回归；检测改进不是模型修复 |
| 原纸船种子42，原生FP16重跑 | 画面通过、MP4哈希相同 | 既有配置与固定样例能够准确复现，不支持把问题一概归因于损坏权重或完全不兼容 |
| 玩具车仅DDIM→DPM，其余不变 | 多数帧空白，末段边缘出现红车 | 更换调度器本身没有使原描述达到可用标准 |
| 同一DPM配置，改为明确居中、小幅移动和丰富场景的描述 | 红车、木桌可见，有轻微运动；主体裁切、细节有限 | 该局部样例通过；没有证明任意描述质量，也未证明单一根因 |
| 按相同验收配置从真实HTTP提交 | 入队、执行、完整解码、Range206、下载哈希、重复提交同ID均通过 | 配置已通过API与执行器传递，网页实际播放至6.125秒结束 |

最终API样例使用`cog2b-dpm20-fp16-v1`：20步、DPM、FP16计算与VAE、CPU FP32文本编码器。生成447.197秒（含降温等待），峰值8,253,398,016字节，49帧/8fps，6.13秒；SHA256 `befaaf6a0eff4595222b1262e7bba52c258f9d7af84830a66a63af677057774f`。助手检查接触表，浏览器完整播放通过，不称用户本人已逐帧审片。

接入代码发现并修正了另外一个明确问题：API此前创建50步/FP32 VAE任务，执行器也未传递VAE精度，与已验收CLI配置不一致。现在API与worker共享版本化配置，保存步数、调度器及精度，执行器版本或字段不匹配时拒绝运行。该修复解决配置传递漂移，不能据此把原短描述的失败归因完全确定或称为通用画质修复。

## 如何处理失败

原结构成功记录保留，同时添加视觉拒绝标记，从作品、选片和导出排除。新任务在退化像素或非有限值处失败；新增多数采样帧空白检查，避免末帧小物体把整段空白拉过平均阈值。保存日志、接触表，诊断任务可保存最终潜变量，从而复查解码而不重复采样。暂停期间后端拒绝提交；当前入口明确标实验预览，不静默改用Wan生成。

这一过程用于展示实验控制、证据保留和服务失败边界。部分提示词退化的根本原因仍未确定，不能把相关性写成已经证明的原因。
